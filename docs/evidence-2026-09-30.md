## Node-RED telemetry monitoring

On 1 October 2026, a monitoring-only Node-RED flow was added to the local
Compose environment. Node-RED v5.0.7 connected to the Mosquitto broker as
`node-red-telemetry-monitor` and subscribed with QoS 1 to:

```text
fleet/vehicles/+/telemetry
```

The flow validates the vehicle ID against the MQTT topic, latitude, longitude,
speed, status and timestamp. Valid and invalid messages are routed to separate
Debug nodes. It does not write to MongoDB, so the ECS telemetry service remains
the single persistence path.

Two controlled messages verified both branches:

- A valid `vehicle-node-red-01` message produced `validation.valid: true` with
  no errors.
- An invalid message produced `validation.valid: false` and reported topic ID,
  latitude, speed, status and timestamp errors.

The Node-RED editor is exposed locally at `http://localhost:1880`. The flow and
both Debug results provide visual evidence of MQTT communication and telemetry
validation without duplicating the production database writes.

## Staged API scaling experiment

On 1 October 2026, the load-balanced `/health` endpoint was exercised in three
stages. This endpoint was deliberately used so the experiment measured the API
and ALB without creating thousands of persistent ride records.

| Requests | Concurrency | Success | Throughput | p50 | p95 | p99 |
|---:|---:|---:|---:|---:|---:|---:|
| 200 | 20 | 100% | 63.40 req/s | 294.29 ms | 513.92 ms | 518.83 ms |
| 1,000 | 50 | 100% | 162.40 req/s | 243.95 ms | 531.48 ms | 1,227.76 ms |
| 3,000 | 100 | 100% | 360.33 req/s | 275.55 ms | 474.09 ms | 523.09 ms |

CloudWatch independently recorded 1,200 ALB requests in the first load minute
and 3,000 in the second. The ALB target response-time average was approximately
3.5–4.0 ms during those minutes, with observed maxima of 61.4 ms and 44.2 ms.
The larger latency reported by the client therefore mostly reflects the
Internet round trip and client-side concurrency rather than application
processing time.

API ECS CPU utilisation remained low: the highest one-minute maximum observed
was approximately 7.1%, below the 60% target-tracking threshold. Consequently,
the service correctly remained at one desired and one running task. After the
test, `telemetry-ingest`, `ride-requests` and `trip-events` each reported zero
visible and zero in-flight messages.

This experiment demonstrates availability and increasing throughput for the
HTTP entry point under a short staged burst. It does not yet demonstrate the
proposal's 500-to-5,000 vehicle telemetry target, sustained auto-scaling, or
matching latency under equivalent ride demand; those require a controlled
telemetry experiment and longer load duration.

## Authenticated telemetry rate experiment

The AWS IoT policy correctly restricts the certificate to connecting as its
Thing name and publishing only to
`fleet/vehicles/vehicle-00001/telemetry`. Therefore, a controlled single-Thing
message-rate experiment was used instead of falsely representing one
certificate as thousands of vehicles.

| Messages | Requested interval | Duration | QoS 1 publish rate |
|---:|---:|---:|---:|
| 50 | 20 ms | 13.38 s | 3.74 msg/s |
| 100 | 0 ms | 26.70 s | 3.75 msg/s |
| 200 | 0 ms | 52.67 s | 3.80 msg/s |

The publisher waited for each QoS 1 acknowledgement, so throughput stabilised
near 3.8 messages per second regardless of the requested interval. This is a
sequential publisher/Internet round-trip limit, not evidence of the maximum
capacity of AWS IoT Core or the backend.

Across all stages, 350 messages were published and exactly 350 matching
`position_history` documents were found in Atlas. The final published and
persisted timestamps both equalled `2026-09-30T16:06:53.475Z`. After processing,
the telemetry queue contained zero visible and zero in-flight messages. The
highest CloudWatch CPU maximum observed for `telemetry-service` was about
7.61%.

This proves loss-free processing for the tested sequential workload across AWS
IoT Core, the IoT rule, SQS, ECS and Atlas. A true 500-to-5,000 vehicle test
still requires provisioned test identities (or an approved fleet-provisioning
policy), parallel MQTT connections and a documented cleanup plan.
